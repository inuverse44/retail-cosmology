# ADR 001: 変わりやすさで層に分ける（The Method）

## Context

このリポジトリの Rust のコードは、計算の手順ごとにモジュールを分けてきた。
ところが、解析の対象が増えるたびに、同じ場所を書き換える必要が出ている。
次の事実は、2026-11-03 にコミット e4682c7 のコードで確かめた。

- 実行ファイル（`crates/retail-cosmology/src/bin/` の `xi`、`osm_census`、`trial_census`）が、ファイルの読み書きと CSV の分割を自分で行っている。三つのファイルで計 16 か所ある。
- オーストラリアに日本を足したとき、`xi` に国による分岐が 7 か所増えた。人口の格子の種類（ABS の GeoTIFF、e-Stat のメッシュ）を、実行ファイルの中の列挙型で切り替えている。
- 人口の格子のモジュール（`popgrid`、`mesh`）は、どちらもファイルの読み込みとランダムカタログの抽出を一緒に持っている。
- OSM のモジュール（`osm`）は、TSV の読み込みと、チェーンごとの店の選び方・地方の割り振りを一緒に持っている。公式サイトのモジュール（`trial_site`）も、JSON の読み込みと業態の選び方を一緒に持っている。

これまでに実際に変わったのは、次の 4 つである。

1. 人口の出どころ：ABS の格子人口に、e-Stat の 1 km メッシュが加わった。
2. 店の出どころ：OSM に、トライアルの公式サイトが加わった。
3. 店の選び方：Coles と Woolworths の規則に、トライアルの規則が加わった。
4. ランダムカタログの重み：陸地に一様と人口に比例に、人が住む格子に一様が加わった。

このあと、ランダムカタログの重みに「都道府県ごとの出店の度合い」（宇宙論の選択関数にあたる）を足す。今の構成のままでは、これも実行ファイルの分岐として増える。

## Decision

Löwy の The Method（References の 1）に沿い、変わりやすさごとに層を分ける。
層ごとの役割と、呼んでよい向きを次のように決める。

1. Client：実行ファイル。引数を読み、Manager を一つ呼び、結果の要約を表示する。ファイルの読み書きと計算はしない。
2. Manager：使用例の手順だけを持つ。このリポジトリの使用例は「店舗の二点相関関数を測る」と「店舗の数を公式の数と比べる」の二つである。Manager は Engine と ResourceAccess を呼ぶ。Manager どうしは呼び合わない。
3. Engine：計算の規則を持つ。店の選び方、ランダムカタログの抽出（重み、つまり選択関数を含む）、対の数え上げ、推定量と誤差の見積もりがここに入る。Engine どうしは呼び合わない。The Method では Engine が ResourceAccess を呼んでよいが、このリポジトリでは呼ばない。Engine は受け取ったデータだけで計算し、ファイルに触れない。
4. ResourceAccess：外のデータの読み書きを持つ。人口の格子、店のカタログ（OSM、公式サイト、選び出した店の一覧）、公式の店舗数、結果のファイルがここに入る。出どころの違い（ABS と e-Stat、OSM と公式サイト）はこの層の中に閉じ、上の層には同じ形で見せる。ResourceAccess どうしは呼び合わない。
5. Utility：どの層からも使ってよい道具。乱数、大円距離などの幾何、地図の投影がここに入る。

呼ぶ向きは上から下だけとする。Client は Manager だけを呼ぶ。

層を分けても、同じ入力と同じ乱数の種からは、分ける前と 1 バイトも違わない結果が出なければならない。
ノートに書いた数字を再現できることを、この判断の前提とする。

The Method のうち、サービスの契約、プロセスの境界、キューによる Manager の呼び出しは採らない。
このリポジトリは一つのプロセスで動く研究用のコードで、それらを入れると、得るものより重さの方が大きいからである。

### 本 ADR で決定しないこと

- モジュール、型、関数の名前とファイルの配置：コード（`crates/retail-cosmology/src/` の各モジュールの文書コメント）に委ねる。
- 選択関数（出店の度合いの重み）の作り方：ノート（`notes/retail-cosmology.tex`）に委ねる。この ADR は、それを Engine の中に置くことだけを決める。
- Python の描画スクリプトと、データを取ってくるシェルスクリプト（`scripts/`）の構成：この ADR の対象外とする。これらは Rust の層の外にある Client と Resource として扱い、README の「構成」の節に書く。

## Consequences

### よい影響

- 国や店の出どころを足すときは、ResourceAccess の実装を一つ足せばよく、実行ファイルと Manager は変わらない。
- 選択関数の重みは、ランダムカタログを撒く Engine の中で閉じる。
- Engine がファイルに触れないので、toy model を渡してテストしやすい。
- どこに何を書くかが、変わりやすさから決まる。

### 悪い影響

- モジュールの数が増え、短いコードでも層をまたいで読む必要がある。
- 今のコードの大半を移すので、移す途中で結果が変わる危険がある。分ける前と後で、すべての出力を突き合わせて確かめる必要がある。
- 使用例が二つしかないので、Manager は薄くなる。

## Alternatives Considered

- 今のまま、必要になったら分岐を足す：コードは小さいままだが、選択関数を足すと実行ファイルの分岐がさらに増える。変わりやすさが実行ファイルに集まり続けるので選ばなかった。
- 国ごとにモジュールを分ける（オーストラリアの解析と日本の解析）：一見わかりやすいが、実際に変わったのは国ではなく、人口と店の出どころ、店の選び方、重みである。国で分けると、推定量や jackknife のような共通の計算が二重になるので選ばなかった。
- The Method をすべて取り入れる（サービスの契約、キューなど）：一つのプロセスで動く研究用のコードには重すぎるので選ばなかった。
