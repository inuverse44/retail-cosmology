## RCA

### P-02：付録の名前の重なりと、差し込みの位置のずれ

- なぜ 1：`\ref{app:…}` が「付録C」と出すことを忘れ、本文に「付録」と書いた。
- なぜ 2：前回も同じ誤りを直したが、そのときは PDF を目で見て見つけただけで、次に防ぐ仕組みを残さなかった。
- なぜ 3：PR の前の確認は、ビルドが通ることと、はみ出し・未定義の参照の grep を毎回その場で書いて行っており、決まった検査として残っていなかった。
- 根本原因：ノートの PR の前に必ず走る検査がなく、一度見つけた誤りの形が検査に足されていなかった。
- 再発防止策（段階 R）：`scripts/check_note.sh` を足し、組んだうえで「付録~\ref」「付録 \ref」、はみ出し、未定義・二重定義の参照を探す。README の手順に書くだけでは段階 0 で、再発した問題には足りないので、git の `pre-push` の hook（`.githooks/pre-push`、`core.hooksPath`）にした。ノートの tex を変えた push のときだけ走り、誤りがあれば push を止める。重なりをわざと戻したコミットで push を止めること、tex を変えない push では 0.04 秒で通ることを確かめた。差し込みの位置のずれは、この検査では見つからない（推定：アンカーの文の後ろに続きの文がないかを見ずに差し込んだ）。これは機械で判定しにくいので段階 1（節を差し込んだら前後のページを画面で見る）にとどめる。

### P-06：振り返りで決めたことが実行されない

- なぜ 1：hook の計画を手元のメモに「次のセッションでやる」と書いた。
- なぜ 2：次のセッションは別の作業（レビューの issue）で始まり、メモは思い出されなかった。
- なぜ 3：振り返りの手順に、前回の予定のアクションと、メモに残したアクションを必ず確かめる決まりがなかった。再発防止策の強さを選ぶ決まりもなく、メモや README（段階 0〜1）で「済み」にできた。
- 根本原因：振り返りの手順が、再発防止策の強さを問わず、予定のアクションを先送りできる形だった。
- 再発防止策（段階 2）：振り返りの skill に、強さの段階（0 記録、1 メモリー、2 CLAUDE.md・skill、3 hook、4 permissions、R リポジトリの仕組み）と、再発したら 1 段以上上げる決まり、予定が 2 回続いたらやるかやめるかを決める決まりを入れた。skill 自体は段階 2 なので、振り返りを始めるときに前回の記録の Try の表を読む手順（§1）で補う。

### P-01：許可の確認で止まる

- なぜ 1：許可リストにない形のコマンドを使った。
- なぜ 2：手早く済ませようとして、ファイルの書き換えに Python の `-c` や `sed -i` を使い、作業フォルダの外のファイルを読んだ。
- なぜ 3：どの形なら確認が出ないかをメモに書いていたが、書き換えの手段を選ぶときに照らしていなかった。
- 根本原因：ファイルの書き換えの手段の既定が決まっておらず、その場で手早い形を選んでいた。
- 再発防止策：書き換えは Edit/Write を既定にし、Python を使うのは確認の出ない形のときにする（メモリ「無人の作業で止まらない」に追記済み）。scratchpad の親フォルダはユーザーが追加の作業フォルダにした。

### P-03：curl が返らないまま待った

- なぜ 1：fetch.sh の curl に `--max-time` がなかった。
- なぜ 2：Overpass の時間切れ（1800 秒）があるので、curl の側にも上限が要ると考えていなかった。
- なぜ 3：バックグラウンドの作業の様子を、通知が来るまで見ていなかった。
- 根本原因：外のサーバーに問い合わせるスクリプトに、時間の上限と失敗したときに止まる決まりがなかった。
- 再発防止策：fetch.sh に `--max-time 2000` を入れた。geocode.sh は `--max-time 30` と「5 件続けて失敗したら止まる」を持つ。メモリ「重い計算は見積もってから」に、curl には必ず時間の上限をつけると追記した。
